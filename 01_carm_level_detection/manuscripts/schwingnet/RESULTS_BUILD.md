# The results-driven build: how the manuscript compiles from the pipeline's outputs

Greg, 2026-09-24: *"I'd like the compile process of the latex to directly reference results files generated by a
reproducible, auditable pipeline, to make even the paper compilation and figure generation reproducible ... it
just says 'XXX Result Pending-JobID' in the sections where the json hasn't been generated. Same for figures."*

## The chain

```
grid jobs  ->  results/*.json (+ figures/*.record.json)  ->  numbers_manifest.json (key -> file#pointer, job)
           ->  tools/results_macros.py  ->  generated/numbers.tex + numbers_audit.md + pending.json
           ->  \usepackage{rsnaresults}: \RESULT{key}, \RESULTFIG{key}, \RESULTSAY{key}{..}{..}
           ->  slurm/compile.sh (runs the generator, then latexmk)  ->  main.pdf, supplement.pdf
```

- **No result number is typed in the prose.** Every quoted result is `\RESULT{key}`. The key's entry in
  `numbers_manifest.json` names the results file, an RFC 6901 JSON pointer into it (the same `file#/a/b~1c` form
  `NUMBERS.md` uses), a format (`fmt`, or `kind`: `kn` for k/n, `ci` for an interval, `pct_of` for a fraction), the
  grid job that produces the file, and a note.
- **A result that does not exist yet** (file missing, or pointer not yet written) compiles to
  `[XXX Result Pending-<job>: key]` in red bold. `tools/results_macros.py --check` exits 1 while any key is
  pending, so the document cannot be submitted with a placeholder and nothing can be invented in its place.
- **Conditional prose**: `\RESULTSAY{key}{text when the result exists}{text while it is pending}` lets a
  conclusion wait for its number instead of being written ahead of it.
- **Figures**: `\RESULTFIG{key}` includes the manifest's file when it is on disk and prints the same marker when it
  is not. In the double-anonymized review copy (`rsnastyle.tex` `\ifcameraready` false, the default; TITLE.md) it
  draws `figures/review/<basename>` when that file exists and the manifest's file otherwise; `tools/check_limits.py`
  lists the fallback per figure and fails if the file drawn carries the network's name (2026-09-25). Each figure is produced by a named tool from results files and writes `figures/<name>.record.json`
  listing every drawn number with its `file#key`; `numbers_manifest.json` can point at those records too.
- **Audit**: `generated/numbers_audit.md` records, per key, the value that was compiled, the source file and
  pointer, the file's SHA-256 and the generation time. The PDF is therefore traceable to the exact result files it
  was built from. `generated/` is rebuilt at every compile and is not edited by hand.

## Rules the check enforces (`python SchwingNet/tools/results_macros.py --check`)

1. No pending key (every manifest key resolves to a value or figure file).
2. No unused manifest key (a key nobody cites is a stale entry).
3. No bare result-looking numeral (a percent, a k/n, a value with an interval) in `sections/results.tex` or
   `main.tex` outside a macro. Years, figure and table numbers are not results.

`tools/check_limits.py` continues to enforce the journal limits and the older `\PENDING{gate}{what}` placeholders;
both checks must pass before a packet is built.
